# Стенд независимого выпуска

Стенд проверяет замену одного артефакта checks при работающих API v1 и reports v1. Подготовленные данные публичны, процессы слушают только локальные адреса. Стенд не передаёт пользовательские или служебные токены. Здесь проверяются выпуск и совместимость; полный сценарий аудита и проверка доступа имеют отдельные примеры курса.

Сервисы находятся в отдельных процессах. Checks хранит результат и outbox в PostgreSQL и отправляет AuditChecked через Kafka. В промежуточной схеме есть `findings` и `issues`; v1 пишет прежний столбец, v2 пишет оба, обе версии читают `findings`. Старый reports читает JSON обычным декодером и хранит контрольные отчёты в памяти. Во время выпуска этот процесс остаётся работающим. API использует один долгоживущий клиент gRPC и circuit breaker.

Подготовленная команда `/fixture/{id}` создаёт небольшой известный результат и outbox. Она служит входом приёмочного стенда и заменяет загрузку страницы. Сохранённый результат содержит одну проблему `missing-content-security-policy` для локальной страницы _/_.

Для интеграционного запуска нужны Go, Docker Compose и готовые PostgreSQL и Kafka. Конфигурация запускает отдельные зависимости стенда.

```bash
docker compose up -d --wait
go run ./cmd/setup
. ./local.env
RELEASE_TEST_DATABASE_URL="$DATABASE_URL" go test -run TestIndependentRelease -v
```

Тест собирает отдельные артефакты checks v1, checks v2, API v1 и reports v1 в своём временном каталоге. Он создаёт случайную схему в тестовой БД и уникальные топик и группу, не очищая таблицы приложения. Тест оставляет свою схему и топик для разбора. Сервисы занимают свободные локальные порты и завершаются после теста.

Проверка последовательно выполняет приёмку кандидата на другом адресе, остановку v1, наблюдение `503`, запуск v2 на прежнем адресе, восстановление долгоживущего клиента и защиты, получение отчёта из нового события старым reports, проверку записи обоих столбцов и возврат v1. Процессы API и reports во время замены сохраняют свои PID.

Матрицу событий можно проверить без внешних зависимостей.

```bash
go test -run TestEventVersionMatrix -v
```

Для ручной проверки собираются те же артефакты.

```bash
mkdir -p .bin
go build -ldflags '-X main.version=v1' -o .bin/checks-v1 ./cmd/checks
go build -ldflags '-X main.version=v2' -o .bin/checks-v2 ./cmd/checks
go build -o .bin/api-v1 ./cmd/api
go build -o .bin/reports-v1 ./cmd/reports
```

После загрузки _local.env_ в каждом терминале запускаются `.bin/reports-v1`, `.bin/api-v1` и `.bin/checks-v1`. Проверка готовности checks обращается к `http://127.0.0.1:8093/ready`. Запрос `POST http://127.0.0.1:8093/fixture/a-before` создаёт контрольный аудит. API читает его через `GET http://127.0.0.1:8080/audits/a-before/result` и `GET http://127.0.0.1:8080/audits/a-before/report`.

Кандидат v2 запускается с параметрами `-grpc 127.0.0.1:9092 -http 127.0.0.1:8094`. Его адрес задан явно, подготовка кандидата использует `/fixture/a-candidate` на порту 8094. После приёмки кандидат останавливается, процесс checks v1 завершается SIGTERM и v2 запускается без переопределения адресов. Старый API продолжает обращаться к прежнему адресу 9090. Откат в этом стенде возвращает `.bin/checks-v1` до удаления столбца `findings`.

Готовые файлы Protobuf включены. Их обновляет `bash generate.sh`. Проверки с повторными событиями и остановкой брокера относятся к отдельному регрессионному прогону и не заменяют приёмку выпуска.
